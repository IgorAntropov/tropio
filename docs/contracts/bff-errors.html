Ошибки BFF и восстановление

HTTP-статус сообщает исход запроса, а машинный code помогает выбрать действие в интерфейсе. После потери ответа команда могла уже сохраниться. В таком случае клиент проверяет известную операцию или повторяет исходный запрос с тем же ключом. Соглашения POC-04

Формат ответа

Отказы POC-04 описаны как application/problem+json со схемой Problem. Проект добавляет к ответам X-Request-Id и Cache-Control: no-store. Identity удостоверяет сессию, Travel и Geo проверяют объектные права. Клиент выбирает реакцию по HTTP-статусу и code. Схема Problem · Границы BFF

  • type — ссылка на тип ошибки, title — краткий заголовок, status — статус HTTP, code — машинный код, request_id — UUID запроса для диагностики.
  • В конфликте могут прийти current_trip_revision_id, current_route_revision_id или current_poi_revision_id. Сервер раскрывает актуальную ревизию только после проверки прав. Клиент перечитывает объект перед новым изменением.
  • Сообщение в интерфейсе объясняет, что произошло и что можно сделать. Для незнакомого кода или ответа шлюза без Problem предлагается общий текст по HTTP-статусу и идентификатор запроса, если он доступен.

Пример конфликта ревизий

{
  "type": "about:blank",
  "title": "Conflict",
  "status": 409,
  "code": "ROUTE_REVISION_CONFLICT",
  "request_id": "21ac6a93-d580-4f82-8958-0dc7c6160a3d",
  "current_route_revision_id": "19fb8843-3032-4062-9e9a-347436bd6ea1"
}

Пример общего ответа при недоступности объекта

{
  "type": "about:blank",
  "title": "Not Found",
  "status": 404,
  "code": "NOT_FOUND",
  "request_id": "93f96c0f-2302-4533-ba1f-efd17c63f405"
}

Когда повторять запрос

  1. Чтение временно недоступно. Повтори GET после восстановления сети или сервиса, пока экран и параметры ещё актуальны. Отменяй устаревшие чтения при смене фильтра или экрана. Поздний ответ не должен заменять данные более нового запроса.
  2. Ответ команды потерян, результат неизвестен. После обрыва сети, таймаута или 503 показывай неподтверждённое сохранение. Если адрес операции известен, опрашивай её через GET. Иначе повторяй исходную команду с тем же Idempotency-Key, ресурсом, ожидаемой ревизией и телом.
  3. Сервер подтвердил конфликт или доменный отказ. Перечитай актуальный черновик или объект, исправь параметры и дай пользователю подтвердить новую команду. Она получает новый ключ. При конфликте ревизий исходные изменения не отправляются поверх новой версии автоматически.
  4. Нужны сессия или права. После 401 или 403 восстанови доступ и перепроверь состояние. При 404 из-за недоступности обнови экран. Восстановление неопределённой команды через исходный ключ возможно только в исходной учётной записи и при действующих правах.

Ключ связан с инициатором, типом и целевым ресурсом. После проверки действующих прав сервис сверяет сохранённый ключ перед сравнением текущей ревизии. Поэтому точный повтор деления может вернуть исходный результат, хотя исходный трек уже заменён. Для завершённых команд POC-04 предлагает окно гарантированного повтора 7 суток. Открытые вопросы

  • Сессия и CSRF. Имя cookie, выдача токена и проверка origin уточняются в GIS-02.
  • Клиентские повторы. Предел автоматических попыток, задержки и поведение между перезапусками клиента нужно определить для конкретных сценариев.
  • Интерфейс ошибок. Тексты общего сбоя, конфликта и подтверждения повторного действия уточняются по сценариям UX-01 и при подключении продуктовых ручек.
